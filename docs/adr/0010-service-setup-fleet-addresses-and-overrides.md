# Services relate to each other by network, Tunnel and one Fleet-wide name; what the user changes is kept as overrides on the Service's record, never in the bundle

Settled in the design session of 2026-11-04 (decisions 295 to 314). The user asked for Services that can lean on each other: a download manager that sends its traffic through a VPN client, Sonarr telling Plex to scan a library, an app on one Node using a database on another. They also asked for fine-grained control over a Service's setup without hand-editing its configuration files. Two parts of what we settled are hard to reverse and would surprise a later reader, so this ADR records them with the model around them.

**A Service has a network choice, one of four.** Its own network, `maitre-<service>.network`, as today; *through a Tunnel*, sharing the Tunnel container's network namespace (`Network=container:<tunnel>`); *on another Service's network*, joining `maitre-<other>.network` so it reaches that Service by name; or *the Node's network*, which is the existing host grant. A **Tunnel** is a Catalog entry marked `tunnel: true`, a Service whose only job is to carry others' traffic. Attaching a Service to a Tunnel rewrites the Tunnel's unit with the attached Pages' ports, so the Tunnel and everything attached restart together; they stop, fail, move and live on one Node together. The Fleet list shows "through <tunnel>" on the attached Service's row; there is no grouping noun and no nesting.

**One name everywhere: `<service>.local`.** People resolve it by mDNS and every Node's Caddy already answers it and hops HTTP to the Node that runs the Service. Containers now resolve it too: the Node answers DNS for its containers (`DNS=` on every Maître network) and gives `<service>.local` the Service's fixed address, the same on every Node. On the Node that runs the Service, its container holds that address. On every other Node the agent holds it, on a dummy interface, listens on the Service's declared ports there (every Page's port plus the manifest's `ports:` and any added in Setup) and carries each connection to the running Node's agent over the Nodes' own mutual-TLS link, which connects to the container. So a Service reaches another at `<name>.local` on the app's own port, as in a Compose file, wherever it runs; nothing is opened on the LAN, and no port is published on any address. A Service is carried only when its "Reachable by other Services of the Fleet" switch is on. The Node's Tailscale is a tsnet node inside the agent, not an interface, so there was no overlay address to publish on; carrying the traffic through the agents was the way to keep the LAN closed.

**One subnet on every Node, and a fixed address per Service that follows it.** Every Node's `maitre` network uses the same subnet, 10.90.0.0/16, with the Node at .0.1 and its DNS at .0.2. The Node allocates each Service an address from it at install, the lowest free across the Fleet's records, keeps it on the Service's record (written as `ip=` on its shared-network line), and the address survives a move to another Node. The user can change it in Setup. This is the first hard-to-reverse choice: the subnet is fixed for the life of a Fleet, since changing it would renumber every Service, and a Fleet-unique allocation on a shared subnet is what lets an address mean the same Service on whichever Node it lands.

**A Service has zero or more Pages.** A Page is a web UI the Service offers: a name, a component, a port and a path, with its own exposure level defaulting from the Service's. The manifest's `web:` becomes a `pages:` list. The sidebar shows one entry for a Service with one Page, a nested list for several and nothing for none; a Service with no Page (a Tunnel, a database) is in the Fleet list only. Routes, frames and the proxy key by Page.

**Edits are overrides on the Service's Fleet record.** Setup, a Console page reached from the Service's flyout and offered at install under Advanced, has the curated settings (network choice, reachability and ports, fixed address, Pages and their exposure, internal network, volumes) and then any `[Container]` key per component, set or removed, checked by the same grant rules as the Catalog. Every change is stored as an override on the record (component, key, value, set or remove), applied after the bundle is rendered, kept across Catalog updates and shown as a diff with per-line reset. The rendered units are shown read-only with each line marked agent-added, template or override. Save previews the unit diff and deploys with a restart. The bundle itself is never modified. This is the second hard-to-reverse choice: once records carry overrides, the override format and its application order are a contract every later version must honour.

**Dependencies are refused or moved, never silently changed.** Removing a Service others lean on is refused and names the dependants. Choosing a network or Tunnel on another Node makes Setup follow the whole dependency chain and offer three choices: move the whole stack to that Node, install a copy of the target on this Node, or do nothing.

## Amendment: a fifth network choice, an address of its own on the home network (decision 327)

Settled on 2026-11-06, when AdGuard Home would not start on Avalon: `listen tcp4 :53: bind: address already in use`, five restarts, then the start limit. Reading the host's own `/proc/net/tcp` from inside the Node's network namespace found three listeners on port 53 — `10.90.0.2:53`, which is this ADR's Fleet DNS, and `127.0.0.53:53` and `127.0.0.54:53`, systemd-resolved's stubs.

**Port 53 of a Node can never be published.** A listening socket on one address blocks a wildcard bind on the same port whatever `SO_REUSEADDR` says, so `PublishPort=53:53` fails before the container runs — Podman reserves a published host port by binding it, which is where the message came from. `Network=host` fails the same way one layer in, with AdGuard binding `0.0.0.0:53` itself. And the Fleet DNS cannot move: Podman's `DNS=` on a network takes an address and no port, so the Node has to answer `<name>.local` for its containers on 10.90.0.2 *at* 53 for as long as this ADR stands. Turning off resolved's stubs would change nothing; they are not the reason.

So the fifth choice: **the Service takes an address of its own on the home network.** Its container joins `maitre-lan.network`, a macvlan over the Node's LAN interface, and holds an address there with a MAC of its own — so it owns every port on that address, 53 included, and the devices of the home are pointed at it rather than at the Node. The Node writes the unit from its own interface, subnet and gateway, read each time rather than once at start, because a macvlan child is on the same wire as its parent and any other subnet would be an address nothing in the home could route to. A wireless or bridge parent is refused with that as the reason.

**Beside the shared network, never instead of it.** The container keeps its `maitre` line and its Fleet address, so Caddy still serves its Pages at `<name>.local` on the Node, the Fleet still reaches it, and its own lookups still go through the Node. The template's `PublishPort` lines are dropped instead, in the renderer rather than in the Catalog, so a Service installed before this is repaired by the next render and not by a reinstall. This also answers the macvlan's one real limitation — the Node cannot reach its own child on that address — because the Node never needs to: Caddy goes over the bridge.

**The address is chosen, not allocated.** Unlike the Fleet address, it has to be outside the router's DHCP pool and it is the address the person types into their router or their devices, so the Node cannot pick it. A Catalog entry says `lan: true` and asks for it as a setting of type `address` under the one key `lan_address`; the Console's existing settings form then asks for it with no special case, and a later edit there reaches the same field. The Node refuses an address off the home network, the Node's own, the router's, the network or broadcast address, and one another Service holds.

**It is a granted option, named `Network=lan`.** A container reachable by every device in the home on every port it answers on gives away as much on the LAN as `Network=host` does, so a Trusted Device signs for it (decision 189). The grant does not name the address, so changing the address later does not ask again.

Two consequences worth stating. An entry with `lan: true` declares no `host_ports` — it holds no port of the Node — and `infrastructure: true` is satisfied by it, where before only `host_ports` would do. And a Service of several containers cannot have one: the address goes to a container, and with several there is no saying which. `adguard-home` and `pihole` are converted; both lose their `PublishPort=53:53` lines and their `host_ports`.

## Considered options

- **A grouping noun (stack, pod, group)**: the user's first instinct, rejected by them; components already cover containers shipped together, and the relationships wanted are between Services the user installed separately. "Group" is also an avoided word in the glossary.
- **Pods for Tunnels**: Podman pods share a namespace, but a pod would make the attached Service a component of the Tunnel in everything the Console shows. `Network=container:` keeps each Service its own Service and Maître manages the coupling.
- **A second name for Service-to-Service reach (`<service>.fleet`)**: one more thing to learn and to type into another app's settings; Caddy already answers `.local` on every Node, so the only missing piece was container DNS.
- **Publishing raw ports on the LAN address**: opens them to every device in the home without a certificate, and was the only publishing possible, since the Node's Tailscale is not an interface. Carrying connections through the agents keeps the LAN closed and works over whichever link the agents have.
- **For decision 327, publishing port 53 on the Node's own address** (`PublishPort=192.168.4.4:53:53`) instead of the wildcard: the smallest change, and it does bind — but an infrastructure Service starts at `basic.target`, ahead of DHCP, so the bind races the address existing and loses for an hour on the start limit when it loses. `net.ipv4.ip_nonlocal_bind=1` is in the image for a Service that ever does publish on a named address, but it is not what makes a DNS Service start. The deeper objection is that the Service would still be sharing the Node's address, so AdGuard's per-client view would be of the Node, and a second DNS Service could never exist.
- **For decision 327, turning off systemd-resolved's stub listeners**: offered itself as the obvious fix and fixes nothing. The Fleet DNS still holds 10.90.0.2:53 and still blocks the wildcard, and the Node would have lost its resolver for no gain.
- **For decision 327, DHCP for the Service's address** (`IPAMDriver=dhcp`): would spare the person choosing one, but a DNS server whose address can move is the one thing it must not be — every device in the home is pointed at it by address.
- **A subnet per Node with addresses translated on a move**: avoids the fixed Fleet subnet, but then an address written into another app's settings stops meaning that Service after a move.
- **Editing the bundle in place**: the user's edits would be lost or conflict on every Catalog update and the signature over the bundle would no longer hold.
- **A text editor over the unit**: what the user asked not to have; the grant check could not tell a curated setting from a raw one, and a Catalog update could not be merged.

## Consequences

- `ServiceSpec` gains the network choice, the reachability switch and ports, the fixed address, Pages and the override list; the Fleet record stores all of them. Overrides have a stable format and a fixed application order: template, then agent keys, then overrides, then the grant check.
- The `maitre` network's subnet is fixed in the agent and written to every Node's `maitre.network` at start; a Node whose network had another subnet stops its Services, recreates it and starts them again, once. Every Service of the Node gets an address then, and units from before are written again.
- The agent gains a DNS server for its containers, a dummy interface holding other Nodes' Service addresses, listeners on their declared ports, and a relay call between Nodes (`/maitre/relay`, Node callers only).
- The Catalog manifest gains `pages:`, `ports:` and `tunnel:`; `web:` is read as a one-Page list until every entry is converted.
- Tunnels need `NET_ADMIN` and `/dev/net/tun`. The grant table promises both, the device untried: a Node has no terminal, so nobody can run a container with it and read the audit log, and the user decided the way to learn whether SELinux allows it is to install the first Tunnel and watch. If `container-selinux` does not already allow `tun_tap_device_t` to `container_t`, the Tunnel fails to start with the denial in its logs and the answer is a rule in the Node image; the device carries only the Tunnel's own traffic, so nothing else is riskier while this is unknown. The first Tunnel entry is `gluetun`.
- The Console's sidebar, routes, frames, proxy header and exposure all move from Service to Page.
- No fallback for Nodes without these features: the user's two Nodes are updated at once.

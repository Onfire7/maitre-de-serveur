# Storage protection: SnapRAID parity and copies chosen per Space, Mirrored Drives for live data, and Drain to empty a Drive

ADR 0004 left room for mirrored copies and SnapRAID parity after v1 without moving any Service. This settles how (decisions 224-260, 2026-10-31). Each Pool stays a MergerFS mount over whole Drives. Protection is chosen per Space, and a Space's files never leave that Space, because a Service's volumes are paths inside a Space's Pool.

**Three kinds of protection, each for its own data.**
- **Parity Level** (Off, 1, 2) on each Space: how many failed Drives its files survive on each Node, from SnapRAID parity on that Node's Parity Drives. Meant for large files that rarely change. New Spaces default to 1; Spaces holding Service app data default to Off.
- **Copies** (1, 2, 3) on each Space: the minimum number of Drives holding each file, kept by a pass the agent runs (the `mergerfs.dup` approach, written in Go).
- **Mirrored Drive**: two whole disks formatted together as btrfs RAID1. It has one filesystem UUID, so Maître sees it as one Drive with tags and Spaces like any other. Copies are written at once and a scrub repairs bad blocks from the good copy. Meant for app data and databases, which neither parity nor copies made by a timed pass protect well.

The Space editor explains parity in these words (decision 224): "Parity lets this Space's files survive a failed Drive, rebuilt from a Parity Drive. It is updated on a schedule, so files changed since the last update are not covered until the next one. It suits large files that rarely change: media, photos, documents. Turn it off for Spaces holding app data or databases. Those change constantly, are rarely covered, and each change weakens recovery for this Node's other Drives. Parity is not a backup: deleted or overwritten files are gone once the next update runs."

**Parity is one SnapRAID array per level per Node (decisions 236, 237, 258).** SnapRAID reads directories, not devices, but each `data` entry must be its own device. So every array has one `data` entry per data Drive at the Drive's root (named by drive id), and `include /<space_id>/` rules for the Spaces at its level. With an include present, everything else is skipped: other Spaces, Unsorted files, Orphan Folders and `.maitre/`. Arrays share the Node's Parity Drives: Parity Drive 1 holds every array's first parity file, Parity Drive 2 the level-2 array's second. A Space cannot get more levels than its Node has Parity Drives; that Node's part shows "Partly protected" with the missing Parity Drive offered. New files of a Spanning Space with a Parity Level go only to Nodes with enough Parity Drives for it, so new data always lands protected; files already on other Nodes stay where they are and stay flagged (decision 258). A non-Spanning Space has nowhere else to put them, so its Node is flagged and the Parity Drive offered. The agent writes the configs from the Drive and Space records; nobody edits them.

**A Parity Drive is a toggle on a Drive (decisions 225, 227, 239-241, 243, 245).** Turning it on shows what will happen and asks for the Drive's name typed, once. It is refused when the Node would have no other data Drive, when the disk also holds another Drive (a partition of the same disk, including the system disk's internal partition), or when the Drive is smaller than the largest amount of protected data on any one Drive. The Drive is then Drained (below). Unsorted files and Orphan Folders move into a Space the user picks, under `<Space>/From <Drive name>/`. Once the Drive holds only `.maitre/`, the agent sets `role = parity` (it then matches no Space rule), formats it btrfs with copy-on-write off for the parity directory, and runs the first sync. If anything else remains, it stops with Attention instead of formatting. A disk not yet adopted can be made a Parity Drive straight away; one holding a Maître parity file from before a reinstall is kept. Turning the toggle off deletes the parity files and returns the Drive to the Spaces its rules match, after a typed confirmation that names the Spaces losing protection. One or two Parity Drives per Node (decision 228); a second is suggested from five protected Drives.

**Syncs are scheduled and guarded (decisions 229-231, 248).** Content files live in `.maitre/snapraid/` on every protected Drive and on the Parity Drive. The schedule is a Fleet default (sync nightly at 03:00, scrub weekly about 8% of data older than 10 days, at idle IO priority), overridable per Node, plus "Protect now". Before each automatic sync the agent runs `snapraid diff`. It skips the sync and puts the Node in Attention when a Drive is missing or empty, or when deletions pass 5% of files or 50 GB. Folders that left an array because of a rule change, and moves on exFAT, do not count toward the threshold. "Protected as of", sync progress and unprotected file counts travel by gossip (ADR 0006), never as records.

**Replace and undelete (decisions 232, 233).** "Replace <name>" formats the new disk, gives it the failed Drive's SnapRAID name, user tags and Spaces, runs `snapraid fix -d` for each array with progress, and keeps the old record with `replaced_by`. Losing a Parity Drive costs each array one level until its replacement is rebuilt. Undelete ("Deleted since last protection → Restore" through `snapraid fix -f`) comes after the first cut. Adopted NTFS and exFAT Drives are protected; the Console says once that exFAT syncs slower (decision 234). The Console shows a Parity card per Node on the Fleet page's Storage area (decision 235).

**Drain empties a Drive without breaking paths (decisions 238, 242, 246, 247).** It runs when a Drive becomes a Parity Drive, when a tag or rule change takes a Drive out of a Space, and later for removing a Drive and drive migration. The Drive stays in the affected Pools as no-create (`=NC`), so its files stay visible. Each Space's files move to that Space's other Drives, this Node's first by the Space's Placement, then, for a Spanning Space without room locally, its Pools on other Nodes, with a warning naming the Node and the time it takes. A non-Spanning Space with nowhere to go blocks the Drain and asks the user to resolve it; there are too many possible fixes to choose one automatically. Files are copied with owners, ACLs, xattrs and hard links, compared by checksum, then deleted from the source. A Service with files open is stopped, its files moved and started again, one at a time, with a notice. A file that already has enough copies elsewhere is deleted instead of moved. The job survives reboots and can be cancelled. Only when the Drive holds none of a Space's files does it leave that Pool, which also fixes today's behaviour: a tag change dropped the Drive from the Pool at once and its files vanished from Services.

**Copies (decisions 249-253, 259, 260).** The agent counts each file across the Space's branches, copies the newest by mtime to more Drives until the count is met, and checks the copy. MergerFS writes to one copy and renames or deletes all of them, so copies drift until they are caught up. The agent watches each Space's folders with inotify (fanotify where a filesystem supports it) and copies a changed file once it has been closed and left alone for a short while; a full pass still runs hourly to catch whatever the watches missed, such as changes while the agent was down or a watch limit reached (decision 260). Copies can be set no higher than the Space's Drives on separate disks: across the Fleet for a Spanning Space, else on its best-stocked Node; higher choices are disabled with the reason (decision 259). Copies go only to Drives on different physical disks. A Spanning Space may tick "Copies on different Nodes when possible" (off by default). Copies and parity may both be on; the editor says two copies already survive one failed Drive. Space cards show usable space beside raw space. A Node that cannot meet the count shows "2 of 3 copies".

**Mirrored Drive (decision 254).** Made from two blank disks, chosen together in the Console, and placed in a Mirrored Space the user picks or creates. A failed disk puts the Drive in Attention, and Replace runs `btrfs replace`. The agent never mounts it degraded on its own.

**A Space is mirrored or plain, never a mix (decisions 255, 256).** A Space takes Mirrored Drives only, or plain Drives only, chosen when it is made, so every file in a Space is protected the same way and the user always knows which files are. A Mirrored Drive never matches a plain Space's rule, whatever its tags, and a plain Drive never matches a Mirrored Space. Changing a Space between the two Drains its Drives of the other kind first. A Mirrored Space has no Parity Level (the editor shows "Mirrored" in its place); Copies still apply, placing copies on more Mirrored Drives, such as on another Node.

**The Protection tab (decision 257).** A Fleet page tab, after Storage: a table of Spaces with Parity Level, Copies and a status per Node; then a card per Node with its Parity Drives, schedule, "Protect now", the Drives that could become Parity Drives, and Mirrored Drives; then running jobs. A held update or a failed Drive shows as a banner above, with its action. Each Space card in Storage keeps Parity Level and Copies, and each Drive row keeps the Parity Drive switch. Spaces are marked by their colour as a left edge, as on the Storage tab's Space cards, not by dots. Prototyped on branch `prototype/protection-tab` (layout A of three).

## Considered options

- **SnapRAID per Drive, every Drive protected**: forces parity onto app data, where constant changes weaken recovery for every other Drive, and makes the Parity Drive as large as the largest Drive instead of the largest protected data.
- **One SnapRAID entry per Space folder**: two entries on one Drive fail together, so one Parity Drive could recover neither. SnapRAID refuses it.
- **One SnapRAID array per Space**: needs its own Parity Drives for each Space. Grouping by level gives the same control with shared Parity Drives.
- **Moving a Space's files into another Space when it has nowhere to go**: breaks every path a Service holds into it.
- **btrfs multi-device pools instead of MergerFS**: one redundancy profile per filesystem, never per folder; RAID5/6 is still not advised for data; losing a disk can damage files across the pool and stops it mounting without `-o degraded`; and it ends Adopt and rule-based Spaces (ADR 0004). Its strength, copies written at once that repair themselves, is kept as the Mirrored Drive.
- **Mirrored and plain Drives in one Space**: a Space's files would be protected or not depending on which Drive MergerFS picked, which the user cannot see.
- **`mergerfs.dup` itself**: a Python script, so the image would need Python, with no progress, checksum checks or state the Console can show.

## Consequences

`DriveRecord` gains `role`, `replaced_by`, `disks`, `draining` and `snapraid_name`; `Space` gains a parity level, a copy count, the different-Nodes option and `mirrored`; the image adds `snapraid` (Fedora packages 15.0). The agent gains the packages `drain`, `parity` and `copies`; `StorageService` gains their calls, every one optional for a Console facing an older Node. Pool assembly must know no-create branches. Parity, copies and Drain are all per Node, so a Node's protection never depends on another Node, except for a Spanning Space's Drain or copies placed on other Nodes. Free space shown for a Space with copies is no longer the Drives' sum.
